C. CROSS-TENANT DEPLOYMENT PRINCIPLES

The target client environment must be independently deployable and independently operable.

Apply the following principles:

- No runtime dependency on the development tenant.
- No shared production database between clients.
- No shared client document storage.
- No deployment-time use of personal developer credentials.
- No hard-coded tenant IDs, subscription IDs, URLs, resource names or secrets.
- No transfer of development secrets to the client environment.
- No silent cross-tenant telemetry or log export.
- No production dependency on a development Azure Container Registry unless explicitly approved.
- No automatic access from the supplier tenant to the client production environment.
- No assumption that the target environment has internet access.
- All client configuration must be externalised.
- Client-specific app registrations, service identities, certificates and keys must be created in the client environment.
- Every client deployment must have its own release manifest, resource inventory and configuration baseline.
- All release artifacts must be immutable, checksummed, scanned and versioned.
- The same approved release package must be deployable through an online, controlled-transfer or offline installation method.

J. END-TO-END USER ACCESS FLOW

Define the complete user-access flow:

1. The user accesses the Docaya web application.
2. The application redirects the user to UAE PASS or the configured identity provider.
3. UAE PASS federates the authenticated identity to Microsoft Entra ID, where applicable.
4. The web application obtains an access token through OIDC Authorization Code Flow with PKCE.
5. The web application sends the access token to API Management.
6. API Management validates issuer, audience, signature, expiry and required scopes.
7. The API validates the user identity and loads application roles and approved attributes.
8. The authorization engine evaluates:
   - role
   - department
   - sensitivity clearance
   - document ownership
   - current workflow assignment
   - document status
   - action requested
   - legal-hold state
   - administrative scope
9. The API permits or denies the action.
10. The access decision is recorded with:
    - user
    - action
    - document
    - evaluated policy
    - decision
    - reason
    - date and time
    - correlation ID
    - source application
11. Only after authorization does the relevant resource adapter execute the requested operation.

Define the claims required in the user token and identify which attributes should come from:

- Microsoft Entra ID
- UAE PASS
- Docaya’s internal user profile
- Department catalogue
- Clearance catalogue
- Workflow assignments
- Document metadata

J. END-TO-END USER ACCESS FLOW

Define the complete user-access flow:

1. The user accesses the Docaya web application.
2. The application redirects the user to UAE PASS or the configured identity provider.
3. UAE PASS federates the authenticated identity to Microsoft Entra ID, where applicable.
4. The web application obtains an access token through OIDC Authorization Code Flow with PKCE.
5. The web application sends the access token to API Management.
6. API Management validates issuer, audience, signature, expiry and required scopes.
7. The API validates the user identity and loads application roles and approved attributes.
8. The authorization engine evaluates:
   - role
   - department
   - sensitivity clearance
   - document ownership
   - current workflow assignment
   - document status
   - action requested
   - legal-hold state
   - administrative scope
9. The API permits or denies the action.
10. The access decision is recorded with:
    - user
    - action
    - document
    - evaluated policy
    - decision
    - reason
    - date and time
    - correlation ID
    - source application
11. Only after authorization does the relevant resource adapter execute the requested operation.
